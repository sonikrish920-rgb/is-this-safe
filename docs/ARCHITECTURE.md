# Is This Safe? — System Architecture

## 1. Overview

Is This Safe? is a browser-based security-awareness tool that helps users evaluate whether a message, email body, SMS text, or link may contain scam or phishing indicators. The interface is designed to be simple and understandable, with an analysis engine that highlights suspicious patterns and explains why a message may be risky.

The application does not require a backend or an API. It runs directly in the browser and processes text locally. IBM Bob was used as a development assistant to build and validate the detection engine; it is not part of the application's runtime.

## 2. Architecture

```
User
  ↓
Input Message / Link
  ↓
Analysis Engine (analyzer.js)
  ↓
Security Signal Detectors (detectors.js) + URL Analyzer (urlAnalyzer.js)
  ↓
Risk Score + Combination Bonuses + Benign Reductions
  ↓
Verdict (SAFE / SUSPICIOUS / DANGEROUS)
  ↓
Warning Signs + Plain-Language Explanation + Recommended Actions
```

The actual implementation follows this flow:

- the user enters content in the textarea and optional URL field
- the app validates the input
- the analysis engine runs all detectors against the combined text
- weighted signals are aggregated with combination bonuses into a risk score
- benign-signal reductions are applied to suppress false positives
- user-initiated-action detection suppresses all combination bonuses for legitimate self-service emails (password resets, sign-in confirmations)
- the score produces a verdict of SAFE, SUSPICIOUS, or DANGEROUS
- the UI renders warning signs, a plain-language explanation, and suggested actions
- recent scans are stored in browser localStorage

## 3. Frontend

The frontend is a static HTML/CSS/JavaScript application.

Structure:

- `index.html` — app shell and UI sections
- `css/style.css` — global layout, colors, spacing, desktop/mobile layout
- `css/components.css` — form fields, buttons, result cards, and history UI
- `css/animations.css` — transitions and motion styling
- `js/app.js` — app behavior, event listeners, loading flow, and storage interactions
- `js/ui.js` — renders fresh result panels using `result.explanation`; history entries persist and replay their stored fields
- `js/examples.js` — sample malicious inputs for demonstration
- `js/history.js` — stores scan results in localStorage

For fresh analyses, the "What this suggests" section displays the distinct plain-language explanation generated by `buildExplanation()` rather than repeating the verdict summary. History entries currently persist `result.summary` in their explanation field.

## 4. Analysis Engine (v3)

The analysis engine is a context-aware, rule-based system implemented in JavaScript. It evaluates security-relevant features in combination, not just isolated keywords.

### 4.1 Key Modules

**`js/analyzer.js`** — Main orchestrator
- Runs all detectors and URL analyzers
- Computes a weighted score from individual signals
- Applies combination bonuses for dangerous multi-signal patterns
- Suppresses all combination bonuses when a `user-initiated` benign signal is detected
- Applies benign-signal reductions to suppress false positives
- Generates verdicts, plain-language explanations (`buildExplanation`), and recommendations
- Engine identifier: `local-v3-context-aware`

**`js/detectors.js`** — Sixteen context-aware detection functions:

| Function | Detects |
|---|---|
| `detectUrgency()` | Deadlines, pressure tactics, service cutoff threats, payment-deadline pressure |
| `detectCredentialRequest()` | OTP, password, PIN, CVV, card number, bank account, national ID requests; handles `your`/`the`/bare-article forms; detects third-party relay ("send the OTP to our support agent") |
| `detectPersonalInfoRequest()` | Name, address, DOB, SSN, Aadhaar, PAN, passport requests distinct from credential capture |
| `detectFinancialRequest()` | Money transfer, payment fees, billing updates, subscription-payment-failed phishing, crypto send requests |
| `detectPrizeScam()` | Lottery/prize claims, "you've been selected", gift card offers |
| `detectImpersonation()` | Brand/authority mentions in exploit context (banks, Apple, Netflix, Google, WhatsApp, government, etc.); suppressed in purely informational/benign context |
| `detectSuspiciousDownload()` | APK, software install, disable-security requests |
| `detectAccountThreat()` | Account suspension/locking, SIM blocking, utility disconnection, KYC threats |
| `detectExternalAction()` | "Click here to verify", "call immediately", "reply with your details" |
| `detectInvestmentScam()` | Guaranteed returns, crypto investment bait, limited-slots pressure |
| `detectSocialEngineeringThreat()` | Vishing (oral code-handover), press-to-connect IVR bait, arrest/legal threats, SIM-porting alerts, third-party OTP relay, cyber-crime-office impersonation |
| `detectHinglishScam()` | Romanised Hindi scam phrasing across five risk categories (credential, threat, demand, urgency, prize); returns structured `categoryCount` for compound scoring |
| `detectCryptoWalletTransfer()` | Bitcoin (legacy/P2SH/bech32) and Ethereum wallet addresses co-occurring with transfer instructions |
| `detectBenignSignals()` | Safety advice, legitimate completion notifications, and user-initiated action confirmations — used to reduce false positives |
| `detectSuspiciousUrl()` | Pass-through wrapper for URL risk scores from `urlAnalyzer.js` (exported but currently called via `analyzeUrl()` directly) |
| `hasNegation()` | Utility: detects negation context around a keyword (exported; currently no callers) |

**`js/urlAnalyzer.js`** — URL extraction and structural analysis:
- `extractUrlsFromText()` — extracts URLs embedded in message text with correct deduplication
- `analyzeUrl()` — scores a URL on structural risk indicators; cap of 20 per URL
- `checkDomainMismatch()` — returns true when the URL domain does not match the brand mentioned in the message

### 4.2 Context Awareness

The engine understands context rather than matching isolated keywords:

- **"Your OTP is 123456. Do not share it."** → SAFE (safety advice detected, no request)
- **"Send the OTP you receive to our support agent."** → SUSPICIOUS (risk score: 29; third-party OTP relay — credential request + social engineering)
- **"Your Amazon order has shipped — track in the Amazon app."** → SAFE (shipped/delivery benign context, impersonation suppressed)
- **"Your Netflix payment failed. Update billing info at http://netflix-billing.xyz"** → DANGEROUS (payment-failed financial request + impersonation + suspicious URL)
- **"Your Apple ID is locked. Verify at http://apple-id-restore.net"** → DANGEROUS (account threat + brand mismatch + suspicious URL)
- **"Win an iPhone! Reply with your name, address, and date of birth."** → DANGEROUS (prize scam + personal info harvest)
- **"Aapka KYC expire ho gaya. OTP abhi share karein."** → DANGEROUS (Hinglish: multi-category credential + urgency compound)
- **"You requested a password reset. This link expires in 10 minutes."** → SAFE (user-initiated, combination bonuses suppressed, benign reduction applied)

### 4.3 Scoring System

Individual signal weights:

| Signal | Score |
|---|---|
| Urgency / pressure | +7 |
| Credential request (OTP, password, card, CVV) | +14 |
| Financial request (payment, fee, billing update) | +14 |
| Investment scam (guaranteed returns, crypto bait) | +14 |
| Crypto wallet transfer (wallet address + send instruction) | +14 |
| Personal info request (name, DOB, SSN, national ID) | +15 |
| Social engineering / coercive authority | +15 |
| Hinglish scam pattern | +15 |
| Suspicious download | +12 |
| Account or service threat | +10 |
| Prize / reward claim | +9 |
| Impersonation (brand mention in exploit context) | +6 |
| External action redirect (click, call, reply) | +6 |
| Suspicious URL | +3 to +20 (capped; depends on URL risk factors) |
| Domain mismatch | +12 |

Combination bonuses for dangerous multi-signal patterns (all suppressed when `isUserInitiated` is true):

| Combination | Bonus |
|---|---|
| Impersonation + urgency + credential request + URL | +18 |
| Credential request + URL | +12 |
| Threat + credential request | +12 |
| Financial + prize (advance-fee fraud) | +12 |
| Impersonation + threat + URL | +10 |
| Financial + urgency | +10 |
| Credential + prize (account-details harvest via prize bait) | +10 |
| Personal info + prize (identity harvest) | +10 |
| Download + URL (malware delivery) | +10 |
| Crypto wallet + urgency | +10 |
| Crypto wallet + investment | +10 |
| Hinglish multi-category (≥ 2 distinct risk categories) | +15 |
| Credential request + urgency | +8 |
| External action + threat | +8 |
| External action + financial request | +8 |
| Personal info + impersonation | +8 |
| Threat + urgency | +8 |
| Social engineering + urgency | +8 |
| Social engineering + threat | +8 |
| Hinglish + credential/financial/personal-info request | +8 |
| Hinglish + prize | +8 |
| Hinglish + account threat | +8 |
| Hinglish + urgency or social engineering | +8 |
| Impersonation + URL | +6 |

Benign-signal reductions (applied only when `hasDangerousRequest` is false):

| Signal | Reduction |
|---|---|
| User-initiated action confirmation (password reset, sign-in) | −15 |
| Safety advice wording | −8 |
| Legitimate completion notification | −5 |

### 4.4 URL Analysis

`analyzeUrl()` evaluates structural risk indicators. HTTPS alone is NOT treated as a safety signal.

Indicators evaluated:

| Check | Score |
|---|---|
| IP address URL | +10 |
| URL shortener | +15 |
| Suspicious TLD (.xyz, .top, .tk, .example, etc.) | +7 |
| Excessive subdomains (> 3 levels) | +4 |
| Generic/test placeholder domain | +5 |
| Deceptive brand keyword in domain | +3 to +8 |
| Brand name buried in subdomain | +8 |
| HTTP instead of HTTPS | +3 |
| Non-standard port | +4 |
| Typosquatting (g00gle, paypa1, etc.) | +10 |
| Unusually long domain name | +4 |
| Suspicious path keywords (reset, verify, secure, login, etc.) | +2 |

The `urlRiskScore` is capped at 20 per URL.

`.test` is handled separately as a generic/test placeholder domain and contributes its own generic/test-domain indicator.

Known legitimate brand domains (e.g., `amazon.com`, `google.com`, `paypal.com`) are not penalised for containing their own brand name.

## 5. Risk Assessment

The application calculates a weighted risk score and maps it to a verdict:

- **0–14: SAFE** — no significant warning signs
- **15–29: SUSPICIOUS** — some indicators; caution recommended
- **30–100: DANGEROUS** — multiple or severe indicators; likely phishing or scam

The score is capped at 100.

## 6. Explainability

The result panel includes:

- a risk-score gauge (0–100)
- a verdict badge (SAFE / SUSPICIOUS / DANGEROUS)
- a list of detected signals with individual descriptions
- a plain-language explanation (`buildExplanation`) naming the specific patterns detected (e.g. "Suspicious because the message claims to be from a known organization, threatens account suspension or service disconnection, and contains a suspicious or mismatched link")
- specific, actionable recommendations

## 7. Test and CI Flow

The test suite is in `js/tests.js` and runs in Node.js with no additional dependencies:

```bash
node --input-type=module -e "import './js/tests.js';"
```

Current test suite: **29 analyzer tests + 2 URL deduplication tests = 31 total**

The GitHub Actions workflow (`.github/workflows/pages.yml`) checks out the repository, then runs this command before the Pages setup and artifact upload steps. The `js/tests.js` runner now sets a non-zero process exit code when tests fail, causing the CI test step to fail and preventing the dependent deployment job from proceeding.

## 8. Security Considerations

- analysis runs on the client side; no request is sent to any remote analysis service
- no user account, login, or backend session is used
- message text and URLs are only processed locally in the browser
- scan history is stored in browser localStorage and is not sent to a server
- no secrets, API keys, or IBM service credentials are required at runtime

## 9. Current Limitations

- the detection engine is based on predefined patterns, not a trained ML model
- it does not query live threat intelligence feeds or URL reputation databases
- it does not verify domain registration, WHOIS data, or certificate authorities
- detection is optimized for English and common Hinglish (romanised Hindi) phrasing; other languages may have reduced accuracy
- highly obfuscated or encoded messages may not be detected
- it is designed for awareness and educational use, not as an authoritative security triage tool

## 10. IBM Bob's Role

IBM Bob was used as a development and analysis assistant to build and validate this engine. It is not part of the runtime application. Specifically:

- Repository history records targeted work across the URL analyzer, detectors, analyzer, UI, tests, CI workflow, and documentation.
- The resulting repository includes the documented local analysis engine and the Node.js test workflow.

No IBM service, model, or API is called when the application analyzes a user message. The deployed application at https://is-this-safe-07.vercel.app/ runs entirely in the user's browser.

## 11. Future Architecture

Realistic future improvements include:

- AI-assisted semantic analysis for more nuanced phishing detection
- real-time URL reputation APIs (e.g. Google Safe Browsing, VirusTotal)
- threat intelligence feeds
- browser extension support
- mobile or desktop wrappers
- multilingual detection beyond English and Hinglish
- more advanced explainability and confidence indicators

These improvements would require additional services or integrations and are not part of the current implementation.
